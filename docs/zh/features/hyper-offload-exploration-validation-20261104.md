# HyperOffload 全局容量探索验证（2026-11-04）

新自动算法的三次稳定步时为 **8.721074／8.818197／9.026081 秒**，运行中位数的中位数为 **8.818197 秒**；相对 PR #15 旧自动算法，配对几何汇总步时降低 **4.8775%**。最好单次为 8.721074 秒。

**8.5 秒基础目标和 8.0 秒挑战目标均未达到。** 验收要求三次均达标；按最慢运行，还需分别降低 0.526 秒（5.83%）和 1.026 秒（11.37%）。这是当前实现的实测差距，不是性能上限的证明。

Profiler日志包含2条内存事件记录不完整提示，原文保存在诊断JSON中。本报告不使用该内存事件记录验收容量，而采用正式训练的逐步分配器峰值和Host池；双rank预定时间线标签已核对，不表示全部内存事件完整。

大卸载方案减少重计算，但实际搬运、执行跟踪和同步开销会增加；释放时刻、反向使用期限及峰值位置约束可用窗口，不能从计算总时长减去DMA总时长推算可任意使用的容量。原始流量为rank0计划中的压缩前逻辑激活字节，不是硬件总线或编码包字节。

Profiler及运行时标记可能扰动执行，区间有重叠、等待与嵌套，不能直接相加为关键路径或可消除收益。原生codec部分DMA未关联方向，已单列。普通raw D2H已有异步流和源存储生命周期保护；`release_device` 常规等待针对H2D目标事件。主机同步和缓存回收是优化线索，未通过无profiler消融量化可回收步时。

两步选策样本与后段稳定窗口存在差异，确认/回退和跨结构探索改善覆盖但仍有限；当前没有穷尽节点组合、批量传输和运行时同步优化，尤其没有穷尽较大卸载结构与压缩的组合及其匹配消融。捕获阶段逐算子事件同步与正常异步重放的条件不同，建模误差大小尚未量化。上述证据解释本轮大卸载为何没有自动变快，不能证明8.5/8.0秒不可实现。

## 压缩、正确性及泛化

三次B最终均实际选择原生SplitZip，三个C均恢复原生码本并执行编码/解码；原始包回退和最坏缓冲预留保留。codec累计包字节只覆盖进入codec的数据，不能替代整步传输字节；结构与压缩一起变化时，全部收益不能归因于压缩。本轮没有相同最终结构下独立三次raw/codec消融的加速结论。

当前源码946项CPU测试及4项subtests、11项原生codec通过；双rank HCCL验证预算、早期候选确认/回退与冻后行为。gated和parallel MLP两种64步合成结构检查完整输出、全部参数梯度/更新、输入梯度及RNG。九次正式Qwen运行每rank579组最终参数/梯度指纹和全部84步探针一致，且实际源码导入、容量与冻结审计通过；这不是每一步全量梯度比较。

生产决策使用结构适配器、实测成本、存储版本、生命周期与峰值，不按Qwen名称、固定层号或张量尺寸特判。实际大模型性能仅验证本轮Qwen配置，不外推其他网络；新的结构须认证适配器。默认40步性能、其他精度/训练长度/优化器和真实跨模型吞吐均未验证。
